# M4 (T8132) PMP test: PMP owns DRAM speed, and starts it low

2026-11-01, Mac mini J773g, linux-gravity-m4 7.1.13.

## Question

GPU reads top out at ~82 GB/s and CPU reads at ~70 GB/s against ~100 GB/s
under macOS (receipts/2026-11-01-m4-decode-bandwidth.md). Nothing on Linux
asks for a DRAM controller (DCS) or fabric speed: the J773g device tree has no
pmgr-misc node and no PMP node. On T8132 the PMP co-processor manages them.
Does starting PMP move the ceiling?

## What was run

- Kernel release 8 = the exact release-7 recipe
  (andreinita21/OmarchyM4Mini packaging/j773g/linux-gravity-m4, GravityLinux
  gravity-m4 @ 4fc326f6c2) plus GravityLinux replacement/115-pmp's T8132 PMP
  and PMP-report drivers, ported to the 7.1 Rust APIs, and
  replacement/000-devicetree's PMP nodes and steady report votes. Files in
  tools/m4-pmp-kernel/.
- The device tree drops the `apple,t6000-pmp-v2` fallback and leaves the GPU
  node alone, so a kernel without T8132 PMP support binds none of it
  (verified after rollback: no PMP driver bound, GPU and bandwidth normal).
- m1n1-gravity 1.6.1 fills the node from the ADT: board-id, DRAM vendor and
  ~60 tunables, among them agx-dcs-bw-threshold / -dvfs-filter,
  ane-{fast,slow}-dcs-bw-threshold, dcs-bw-threshold, dvfs-domain.

## Result

PMP started ("io.cpp:54: PMP started"; report finalize: bit 12 enabled, bit 18
dropped, both ret=0). Then:

| | release 7 (no PMP) | release 8 (PMP on) |
|---|---:|---:|
| CPU read, 1 thread | 34.2 GB/s | 17.8 GB/s |
| CPU read, 10 threads | 69.3 GB/s | 21.0 GB/s |
| GPU | 81.7 GB/s read | firmware crashed at boot |

GPU firmware, 4 s after boot (never seen in the three earlier boots):
`agfMTRAlarmHandler: !!! Fatal Error: Received MTR Alarm interrupt from GPU
but no match found in MTR hardware! chainID=0`.

Rolled back to release 7 (a package rebuilt from the installed files):
GPU 81.8 GB/s, CPU 73.3 GB/s, no crash.

## Reading

- PMP does own DRAM speed on T8132: with it running, CPU bandwidth fell to
  30% and stayed there, so it parked DCS at a low state and nothing told it
  to raise it. Without PMP, DCS stays at the state iBoot left, which is fast
  but evidently not the top one (~70-82 vs ~100 GB/s).
- PMP raises DCS from bandwidth monitors (the agx/ane/afi *-bw-threshold and
  -dvfs-filter tunables) and from performance votes. The GPU firmware's MTR
  alarm path crashed on the first PMP-driven event; in GravityLinux's tree
  the GPU node is disabled, so PMP has likely never run beside a live M4 GPU
  firmware there.
- So the remaining ~20% is reachable only through PMP (or a direct DCS
  request, which on T8132 is PMP's job), and that needs the GPU firmware side
  (whatever MTR expects to be configured) before PMP can stay on.

## Root cause of the GPU crash (same day)

MTR is the GPU's temperature-sensor (metrology) block. Read from the running
G16 firmware (mBoot-18000.161.10; code at GPU VA 0xfffffc0000d28000, found by
walking iBoot's UAT handoff tables; dumps stay local, not published):

- `agfMTRAlarmHandler` (0xfffffc0000d5c814) loads a sensor mask from offset
  0x3b58 of the hardware-data block the driver builds. For each set bit i it
  reads MTR status at register 0x1008 + i * 0x200 (alarm bits 27:24). No set
  bit, or no status in any masked sensor, ends in "Received MTR Alarm interrupt
  from GPU but no match found in MTR hardware!" (the crash we saw).
- A matched alarm is then "handled" only through the fast-die masks at 0x2f08
  (shifted by the word at 0x2f14) or 0x2268; otherwise "MTR Alarm interrupts
  not handled!" (also fatal).
- At start-up the firmware arms alarms only for sensors in those masks: for
  each bit of 0x2268 it writes 0x1000000 to MTR 0x1004 + i * 0x200, for 0x3b58
  0x10000 (when a firmware flag is set), for 0x2f08 1 << (24 + shift).
- linux-gravity-m4's G16 driver (g16_platform.rs `hwdata()`) leaves 0x2268,
  0x2f08 and 0x3b58 at 0. siliconforest-linux's M3 (T8122) board writes the
  ADT fast-die mask to 0x2268 and 0x2f08 and 0x4b48 to 0x3b58 (plus 1 at
  0x3b60): the same offsets in the same object.
- PMP's ADT temp-sensor table includes "MTR_TOP_AGX" with a 109 C threshold
  (the CPU and ANE sensors at 110/125 C). PMP arms that GPU sensor itself; the
  GPU firmware, told to watch no sensors, has nothing to match the interrupt.

Across known chips the alarm mask contains the fast-die mask (M1 0x12/0x12, M2
0x6800/0x6800, M1 Pro/Max 0x80/0x90 per byte, M3 0x4248/0x4b48). The M4
driver's fast-die controller uses 0x6958 (bundle +0x75e8), the likely set.

Fix to test: write the sensor masks at 0x2268, 0x2f08 and 0x3b58 (kernel
parameters, default off), and bisect with the two fatal messages: "no match"
means the alarming sensor is outside the 0x3b58 mask, "not handled" means it is
inside it but outside the fast-die masks.

## Mask fix test (release 10)

asahi_m4 gained three parameters (default 0, data unchanged): mtr_alarm
(power-parameter object +0x3b58, bundle 0x8ed8), mtr_fast_die (+0x2268 and
+0x2f08) and mtr_alarm_flag (+0x3b60). (Release 9 wrote them into the
hardware data at bundle +0 by mistake and changed nothing.) With PMP on and
mtr_alarm=0x6958:

- The G16 firmware no longer crashes at boot (it did on releases 8 and 9).
- The first GPU job fails within 7 ms ("failed Event kind=4", stamp never
  written); no failed events on the normal kernel.
- CPU DRAM reads stay at 21 GB/s (69-73 without PMP).
- Two DCP (display) co-processor crashes at boot, new to this boot; the
  login screen still came up.

So the mask removes the fatal alarm, but PMP and the G16 firmware still don't
cooperate, and PMP keeps DRAM parked low. Next suspect: the GPU firmware's
channel to PMP (older chips map a "PMPDoorbell" region; the G16 driver maps
none) through which it would request GPU and DRAM performance.

## Why the GPU job stalls and DRAM stays low (release 10 analysis)

- The failed event is kind 4 with event_slot -1 and counter 0: in Asahi's
  older-firmware numbering that is the firmware's own GPU timeout with no
  slot. The G16 driver only handles kinds 1, 6, 7 and 13.
- PMP's ADT dcs-bw-threshold table has six DCS (DRAM) states with up/down
  thresholds (16.16 GB/s): up at 19.9, 39.9, 58.0, 74.3 and 87.0 GB/s. Our
  measurements fit: no PMP, 70-82 GB/s (iBoot leaves DCS in state 4, <= 87);
  macOS ~100 GB/s (state 5); PMP running, 21 GB/s (state 0-1).
- PMP raises DCS from bandwidth monitors and performance requests. Our PMP
  driver performs only the start-up handshake; nothing sends PMP performance
  requests (the same is true of GravityLinux and aurora-silicon's PMP work so
  far), so it holds DRAM, and probably the GPU, low.
- The G16 firmware knows a kAGFIPIORegionTypePMPDoorbell region, but among
  Asahi's tables only M1 (T8103) maps one; the region names are not
  referenced from G16 code, so the slot mapping is not visible there.

Next: release 11 = release 10 with apple_pmp.verbose=1 by default, to log
every descriptor PMP asks for and which tunables it does not receive.

| | no PMP (r7) | PMP, 4 monitors (r10/r11) | PMP, all monitors (r12) |
|---|---:|---:|---:|
| CPU read, 1 thread | 34 GB/s | 18 GB/s | 9.6 GB/s |

PMP acts on the monitors, but in the power-saving direction: nothing votes
for performance, so it lowers DRAM further. The missing piece is a
performance vote. aurora-silicon/linux m4/pr1-basic-bringup does this

stride 0x4000, AP agent 3, dcs_max 5, pending bit at voters + 4,
apple,static-voters = <3>) with CLPC voting DCS 5 / SOC 3 under CPU or GPU
load; their G16 maps the PMP report pages (slots 9/10, which the GravityLinux
G16 driver also maps) and places a PMP AGX vote before RUN. Porting PMC/CLPC
voting is the next step; until then PMP stays off.

## PMC voting fixes DRAM (releases 14-15)

Ported aurora-silicon m4/pr1-basic-bringup's PMC voter driver
(drivers/pmdomain/apple/pmc.c, include/linux/soc/apple/pmc.h) and T8132 CLPC
floors (drivers/soc/apple/clpc.c) to 7.1.13 (port_pmc.py). J773g DT: a
separate pmc@382800000 node (compatible apple,t8132-pmc, voters
0x382800000+0x10000, rails 0x3828aa000+0x3000, apple,pmp, static voter 3)
with the CLPC child at agent 3 (apple,gpu-power-state = <&ps_gfx>). CLPC
samples every 4 ms and, while a CPU cluster is >= 50% busy or ps_gfx is on,
votes DCS 5 / fabric 3 through agent 3; it releases after 32 ms idle.

- The base DT already has power-management@382800000 (the DCP firmware's
  "dcp-fw-pmgr" bandwidth-scratch window, 0xbc000, used through
  apple,bw-scratch at +0x20000/+0x2c000/+0x34000). Merging the PMC into that
  node would have shrunk it; the PMC gets its own node instead. DCP only
  reads the address (of_address_to_resource), so the two coexist.
- Release 14: PMC probe failed with -EBUSY: its rail-enable words (rails +
  0x2000 = 0x3828ac000) are the registers pmp-report maps as "event-config"
  for its post-ready staging. Release 15 maps the PMC rails window without an
  exclusive claim (pmc_shared_rails.py).

Release 15 (PMP + MTR mask + all monitors + PMC/CLPC):

| CPU read | no PMP (r7) | PMP alone (r10-r12) | PMP + PMC/CLPC (r15) |
|---|---:|---:|---:|
| 1 thread | 34 GB/s | 18 (r12: 9.6) | **36.0** |
| 4 threads | 57 | 21 | **69.1** |
| 10 threads | 69-73 | 21 (r12: 13.3) | **83.6** |

DRAM now runs above iBoot's default, the first time on this machine. The
GPU still hits the firmware timeout (kind 4) on its first job. aurora-silicon
m4/pr2-gpu-dcp routes the AGX (and display) votes as PMP firmware commands
("expose retained PMP display and GPU ownership": pmp.rs +130,
pmp-display.c, pmp-power-policy.h) and gates ps_gfx under a GFX TVM domain
(apple,t8132-gfx-tvm at 0x380760800). Porting that GPU vote is next.

## GPU under PMP: votes, gate and a control (releases 16-18)

- Release 16 sends aurora-silicon's PMP device-power votes once PMP is ready
  (pmp_power_votes.py): command 0x0f for AGX (device 5) and DISP (device 8),
  words 0x0020f50100000000 / 0x0020f80100000000. PMP acknowledged both with
  0x0021000000000000 within 1 ms. CPU reads 35.7 / 69.6 / 86.0 GB/s (1 / 4 /
  10 threads). GPU: same firmware timeout.
- A read-only /dev/mem peek (regpeek.py) on release 16: GFX TVM gate
  0x380760800 = 0 (off) with ps_gfx on; PMC agent 3 floor 0x35 (DCS 5,
  fabric 3: CLPC's vote); rail 0/1 enable 0xd (agents 0, 2, 3).
- Release 17 adds aurora-silicon's GFX TVM gate as ps_gfx's parent, switched
  on at probe (tvm/gfx-tvm.c): the gate went 0x0 -> 0x1, both votes were
  acknowledged, the GPU still timed out. The firmware takes the job (queue
  done = 1) but never writes its stamp; ~9 ms later it posts event kind 4
  (event_slot -1).
- Release 18 is the control: release 17 with apple_pmp.enable defaulting to
  0. The GPU works (81.8 GB/s, no failed events) with the MTR mask and the
  TVM gate on; the gate also reads 0 at boot there, so it is not needed.

So the GPU fails only while PMP runs. The G16 firmware has
"AGFHALWaitForPerfState" and "VCM perf state change timeout": with PMP
running it most likely hands GPU voltage/performance changes to PMP and waits
for an acknowledgement our stack does not produce. Our driver already maps
the PMP report pages into the GPU (slots 9 and 10 = 0x3803d0000 and
0x3803c0000, which hold the report's update window 0x10c40 and read windows
0x1880/0x1900). Next: find what the firmware waits on (disassemble
AGFHALWaitForPerfState and its PMP-side writes).

Status: DRAM fixed (PMP + PMC/CLPC: 86 GB/s CPU, from 69-73); GPU with PMP
still blocked. The Mini runs release 18 (PMP off, GPU working).

## Where the GPU firmware waits (same day)

`AGFHALWaitForPerfState` (firmware 0xfffffc0000d5431c) polls the GPU
perf-state status register at physical 0x300e01000 (low 5 bits) until it
equals the requested state. On a timeout it logs "PIO poll ... continue wait"
and keeps polling, so it never gives up. With PMP off (release 18) the
register reads 3 at idle and switches to 0xa within one sample under load
(0x300e01100 goes 0xe0000000 -> 0x60000000). Full 0x300e00000 block dumps at
idle and under load: `~/gpu/pmp_ab/clk/r18-{idle,load}.txt` on the Mini.
With PMP running, the state switch apparently never happens. That fits a GPU
voltage/clock (DVFM) step that PMP now owns and our stack never requests.

## Boot hang after the TVM gate (releases 17-18)

The reboot from release 18 into release 17 never came back. Every later boot,
including cold starts after holding the power button, stayed black, with no
journal entry, while macOS booted normally. The boot menu is hidden
(`quiet: yes`, 1 s timeout), so a black screen gave no hint of the stage.

Recovered from macOS on the same Mini. The Linux ESP (`EFI - OMARC`, FAT32,
disk0s4) mounts with `sudo diskutil mount`:

1. `apple_pmp.enable=0` added to the limine cmdline: still black. PMP is not
   the cause.
2. Verbose limine (`quiet: no`, 10 s, `loglevel=7`): still black.
3. Restored `m1n1/boot.bin.old`, the m1n1 stage 2 built at the release-16
   install, whose DT has no `gfx_tvm` node: **Linux boots** (release 17
   kernel, PMP off, GPU 81.8 GB/s). Release 17's stage 2 is kept as
   `m1n1/boot.bin.r17-tvm`.

A dtc diff of the two stage-2 DTs shows that the only difference is the TVM
gate node plus `&ps_gfx { power-domains = <&gfx_tvm>; }`. update-m1n1 keeps
`.old` only when the image changes, so the hung boots used the very stage 2
that booted releases 17 and 18 (warm reboots, gate switched 0x0 -> 0x1 both
times). The hang is therefore intermittent, not a bad file. After recovery,
0x380760800 reads 0 again, so no gate state survives. The GPU works without
the gate, so release 19 drops it.

Release 19 (pmp_runtime_start.py) drops the TVM gate. It boots with PMP off
and can start PMP after boot:

    echo 1 | sudo tee /sys/module/pmp_report/parameters/pmp_enable
    echo 380500000.pmp | sudo tee /sys/bus/platform/drivers/apple_pmp/bind

Writing 1 also re-runs pmp-report's post-ready finalize (bits 12/18, AGX/DISP
votes). If the GPU then hangs, a power-cycle comes back to the PMP-off state.
No ESP repair is needed.

## Release 19: PMP started live, GPU perf state captured

Release 19 booted in about 70 s. `pmp_live.sh r19` ran these steps:

1. Baseline with PMP off: GPU 81.6 GB/s, CPU 69.9 GB/s (10 threads).
2. Set `pmp_enable` and bound `apple_pmp`. PMP started ("io.cpp:54: PMP
   started"), the post-ready bits 12/18 took, and the AGX and DISP votes were
   both acknowledged within 1 ms. PMC and CLPC probed: CPU went to 85.5 GB/s.
3. One GPU job: `DRM_IOCTL_ASAHI_SUBMIT` gave EIO after the same event kind 4
   (stage 0, event 34, done=1, stamp never written, age 8 ms).
4. After that the GPU driver is dead (`vkEnumeratePhysicalDevices` = -3).
   That gives one GPU-under-PMP sample per boot.

GPU perf-state block (0x300e0xxxx), words that differ:

| reg | PMP off idle | PMP off load | PMP on idle | PMP on, job |
|---|---|---|---|---|
| 01000 perf state | 3 | 0xa | unreadable | **1** |
| 01100 | e0000000 | 60000000 | e0000003 | e0000000 -> 60000000 |
| 01350 | 80090cd3 | 800**e**0e24 | 00080cce | 800**8**0d2a |
| 01368-013d8 (x14) | 0x22c | **0x230-0x232** | 0x2c | **0x22c** |

Reading: with PMP off, a GPU job raises the field at 01350 bits 16-19 from
9 to 0xe, and the fourteen 0x22c readings at 01368-013d8 (voltage-like)
step up to ~0x231 while the perf state goes 3 -> 0xa. With PMP on, the job
asks (01100 flips to 0x60000000, as under load) but the level drops to 8,
the readings stay at 0x22c and the state reaches only 1.
`AGFHALWaitForPerfState` waits for the requested state, so the job never
starts. At idle, PMP gates the block itself (most words unreadable, readings
0x2c, top bit of 01350 clear), which is expected power management.

Conclusion: under PMP the GPU's voltage/clock raise needs PMP's grant, and
PMP never gives it. The AGX device-power vote (command 0x0f, state 1) is
acknowledged but evidently not enough. Next: find how the GPU firmware or the
AP asks PMP for a GFX performance level, e.g. a perf-state table PMP must be
given, or the report page update window (0x3803d0c40), which the GPU firmware
has mapped.
Captures: `~/gpu/pmp_ab/live/r19-*.txt` on the Mini.

## Firmware: the perf-state change path

Disassembled from the dumped G16 text (va 0xfffffc0000d28000; offsets below
are relative to it). `AGFHALWaitForPerfState` (0x2c31c) has a single caller,
the perf-state change routine at 0x2e560:

1. 0x2e65c-0x2e6f4: `AGFHALWaitForMGPUReqCleared` polls bit 4 of
   0x300e01000.
2. 0x2e7a8: `0x3d2bc(0, state)`. 0x3d2bc is a stub around the Apple
   instruction 0x00201424 (a GXF call into the privileged layer), so the
   request itself is written by code that is not in this dump.
3. 0x2e7cc: a config word at `+0xf38` picks the wait. When it is 0, the
   routine polls with `AGFHALWaitForPerfState` (where we stall). Otherwise it
   uses an event wait (0x47e54).
4. 0x2e950: only after the state is reached, `0x4ea28(5, 2, state |
   0x2000000000000000)`. Its error string is "PTD write failed (%u, %u)": the
   firmware writes the new GPU state into PMP's device table (device 5 = AGX,
   field 2) at PTD space + 0x10000 + 8 * entry, the same window as
   pmp-report's 0x10c40 update area (loader slot 9 = 0x3803d0000).

The firmware's I/O region names include `kAGFIPIORegionTypePMPDoorbell`,
`kAGFIPIORegionTypeAONPTDSpace`, `kAGFIPIORegionTypeDVFMMgpuRegisters` and
`kAGFIPIORegionTypePMCRegisters`, plus "VCM perf state change timeout after
%uus (VCM_PERF_STATE_CONTROL = %x)". So under PMP the GPU is expected to
reach PMP through a doorbell and the PTD space, with voltage handled by a VCM
block. Open questions for the next pass:

- which loader slot macOS fills with the PMP doorbell (our table maps only
  the PTD pages, slots 9 and 10);
- what the `+0xf38` word is and what macOS sets it to;
- whether PMP needs the GPU's DVFM/voltage table before it will grant a raise.

## Release 20: hardware-data policy words (negative result)

Following `[[0xfffffc0000eba758]] + 0xf38` live showed that the word the
perf-state routine checks is at offset 0xf38 of our driver's hardware-data
bundle (BUNDLE_ADDRESS 0xfffffc20c04d8000; the main config at +0x1da40 points
back to it), and that it is 0. Asahi's HwDataB sets the matching fields to 1
on every chip (unk_4f0/unk_4f4, shifted +0xa44). GravityLinux's newer G16C/G17P
driver (replacement/210-gpu, scheduled_hwdata.rs, MAX_POLICY) sets 0xf04 =
0x1f, 0xf34 = 1, 0xf38 = 1 and 0xf4c = 0x31. Its G16G path, like ours, leaves
them 0.

Release 20 (hwdata_set.py) adds `asahi_m4.hw_set0..3` ((offset << 32) |
value). We booted with those four words set (dmesg confirms each write). Then
`pmp_r20.sh r20`:

- PMP off: GPU 81.8 / 81.9 GB/s, perf state 3 at idle. The words do not hurt.
- PMP started live: votes acknowledged, CPU 83.6 GB/s, perf state 1 at idle
  (it was unreadable/0 in release 19).
- GPU job: the same failure. Event kind 4, stage 0 / event 34, stamp never
  written, `age_ms=13`. The perf state stays 1 throughout, and the driver is
  dead afterwards.

So the policy words are not the missing piece. The failure also comes about
10-13 ms after submission in every run, while `AGFHALWaitForPerfState` would
poll forever. So the job is probably not stuck in that wait. Some other
firmware wait with a ~10 ms budget expires while PMP runs. Candidates for the
next pass: the GPU's power-on of its shader cores (Fender power-transition
region) or another PMP-owned step reached through the unmapped
`kAGFIPIORegionTypePMPDoorbell`.

### Looking for the firmware's own message (fwlog_cap.sh)

The firmware's poll helpers log the register they waited on ("PIO poll ...
timeout after %uus [type:%d reg:0x%x expected:0x%x got:0x%x]", and "Fatal
Error: ... Poll timeed out. Caller timeout value = %u uSec"). The helpers have
35+ callers, so the code alone does not say which one fires. Our driver starts
only RTKit endpoints 0x20/0x21, and nothing prints firmware log text (the GPU
does not use RTKit syslog, unlike PMP).

We dumped the firmware region (0x10001150000+0x13c000) before PMP, after PMP
start and after the failed job. No log text appears in it, and the changed
pages (stack-fill `RTKSTACK` areas, 25 pages) hold no text return addresses,
so the waiting thread's stack and the log ring live elsewhere. Next step:
give the G16 firmware a log channel (or find where it writes its log) so the
failing wait names its register.

## G16 firmware log reader, and what it says about PMP

The firmware's log function (0x34eb8) writes into rings that the main config
already points at, from a macOS-derived layout:

- `main+0x1d0`: ring state at 0xfffffc200003f200, 9 channels x 0x30.
- `main+0x1d8`: headers at 0x...43c40, 9 x 256 x 0x48.
- `main+0x200`: payloads at 0x...6c440, 9 x 256 x 0xd8. Each entry holds
  type 3, a count, a timestamp and up to 200 bytes of text at +0x10.

The sizes tile exactly up to the next table address (0x...e5c40). The only
missing piece is the enable word at `main+0x250`, which was 0. Release 20's
`hw_set0 = (0x1dc90 << 32) | 1` sets it (main config = bundle + 0x1da40), and
`fwlog_read.py` prints the log through the firmware page tables. With the log
on, the GPU still works (81.9 GB/s).

The boot log:

    G16 Firmware initializing / FW Build variant: g16g / version: b0
    AGFACREInit: CRE has no restore data and will save registers this run.
    Invalid AON PTD Dev Instance, Was AON PTD initialized?
    AON PTD Enable mask is 0 for mGPUS. Skipping!
    AON PTD Enable mask is 0 for Fabric. Skipping!

The failing job under PMP logs nothing new, so the ~10 ms timeout is not a
logged poll. The boot messages, though, show that the GPU firmware never
registers with PMP's device table (PTD):

- The device ids and enable masks live in the power object (`[main+0x469]`,
  bundle 0x5380): ids at +0x6320, mGPU mask at +0x6360, fabric id/mask at
  +0x6368/+0x6370. GravityLinux's G16C/G17P driver (replacement/210-gpu,
  scheduled_power.rs) sets "g0TR".."g3TR", mask 0xf and "r0TR"/1; its G16S
  variant sets mask 3 with g0TR/g1TR. Our G16G driver sets none of them.
  With g0TR/g1TR and mask 3 set through `hw_set`, the mGPU warning goes away.
  The firmware then tries both devices and logs "Invalid AON PTD Dev
  Instance" for each.
- The instance (firmware global 0x150100) is built only when the auxiliary
  table at power object +0x6318 (bundle 0xb698 -> 0xfffffc20c0500000) has
  entries: 12-byte records (u8 id, u16 base at +2, u16 count at +4, flags at
  +8), up to 19, looked up by id (0x4e9cc). Ours and GravityLinux's are a
  zeroed page.
- The data exists in PMP's device tree node. `apple,tunable-ptd-range` holds
  0x20-byte records (u32 id, base, count, extra, 16-byte name). Examples:
  2 PMP-STATUS @1, 3 DVFS-STATE @8, 5 PMS-PMGR-PKT @0x10, 9 SOC-DEV-PKT @0x30,
  0xa SOC-DEV-PS-REQ @0x188 (pmp-report's own 0x10c40 write slot =
  0x10000 + 0x188 * 8), 0xb SOC-DEV-PS-ACK @0x190, 0xc SOC-DEV-DVFS @0x198.
  `apple,tunable-pm-ptd-ranges` lists the power-management subset (ids 1-7,
  9-0xd, 0xf).

The instance's init (vtable at firmware data 0xdb0058 -> text 0x4380c,
message 1) takes the auxiliary table and its count (the highest non-empty
12-byte slot, at most 19). It sorts the records by their first u32
(0x43950), registers them for the id lookup (0x4e9cc: u8 id at +0, u16 base
at +2, u16 count at +4, flags at +8) and allocates its 32-slot request pool.
A PTD write then lands at PTD space + 0x10000 + 8 * (base + field), inside
the mapped loader slot 9 (0x3803d0000, 512 entries). On G16G the fabric
loop reads its ids at power object +0x6378 and its mask at +0x637c, not
G16C's +0x6368/+0x6370.

Release 21 (`ptd_setup.py`, not yet built) adds `asahi_m4.ptd_setup`,
default 0:

- **bit 0:** pmp-report's new `apple_pmp_gpu_ptd_ranges()` builds the
  auxiliary table from `apple,tunable-ptd-range` (13 power-management ranges
  per `apple,tunable-pm-ptd-ranges`).
- **bit 1:** g0TR/g1TR with mGPU mask 3.
- **bit 2:** r0TR with fabric mask 1.
