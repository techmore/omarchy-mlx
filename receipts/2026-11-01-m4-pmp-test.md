# M4 (T8132) PMP test: PMP owns DRAM speed, and starts it low

2026-11-01, Mac mini J773g, linux-gravity-m4 7.1.13.

## Question

GPU reads top out at ~82 GB/s and CPU reads at ~70 GB/s against ~100 GB/s
under macOS (receipts/2026-11-01-m4-decode-bandwidth.md). Nothing on Linux
asks for a DRAM controller (DCS) or fabric speed: the J773g device tree has no
pmgr-misc node and no PMP node. On T8132 the PMP co-processor manages them.
Does starting PMP move the ceiling?

## What was run

- Kernel release 8 = the exact release-7 recipe
  (andreinita21/OmarchyM4Mini packaging/j773g/linux-gravity-m4, GravityLinux
  gravity-m4 @ 4fc326f6c2) plus GravityLinux replacement/115-pmp's T8132 PMP
  and PMP-report drivers, ported to the 7.1 Rust APIs, and
  replacement/000-devicetree's PMP nodes and steady report votes. Files in
  tools/m4-pmp-kernel/.
- The device tree drops the `apple,t6000-pmp-v2` fallback and leaves the GPU
  node alone, so a kernel without T8132 PMP support binds none of it
  (verified after rollback: no PMP driver bound, GPU and bandwidth normal).
- m1n1-gravity 1.6.1 fills the node from the ADT: board-id, DRAM vendor and
  ~60 tunables, among them agx-dcs-bw-threshold / -dvfs-filter,
  ane-{fast,slow}-dcs-bw-threshold, dcs-bw-threshold, dvfs-domain.

## Result

PMP started ("io.cpp:54: PMP started"; report finalize: bit 12 enabled, bit 18
dropped, both ret=0). Then:

| | release 7 (no PMP) | release 8 (PMP on) |
|---|---:|---:|
| CPU read, 1 thread | 34.2 GB/s | 17.8 GB/s |
| CPU read, 10 threads | 69.3 GB/s | 21.0 GB/s |
| GPU | 81.7 GB/s read | firmware crashed at boot |

GPU firmware, 4 s after boot (never seen in the three earlier boots):
`agfMTRAlarmHandler: !!! Fatal Error: Received MTR Alarm interrupt from GPU
but no match found in MTR hardware! chainID=0`.

Rolled back to release 7 (a package rebuilt from the installed files):
GPU 81.8 GB/s, CPU 73.3 GB/s, no crash.

## Reading

- PMP does own DRAM speed on T8132: with it running, CPU bandwidth fell to
  30% and stayed there, so it parked DCS at a low state and nothing told it
  to raise it. Without PMP, DCS stays at the state iBoot left, which is fast
  but evidently not the top one (~70-82 vs ~100 GB/s).
- PMP raises DCS from bandwidth monitors (the agx/ane/afi *-bw-threshold and
  -dvfs-filter tunables) and from performance votes. The GPU firmware's MTR
  alarm path crashed on the first PMP-driven event; in GravityLinux's tree
  the GPU node is disabled, so PMP has likely never run beside a live M4 GPU
  firmware there.
- So the remaining ~20% is reachable only through PMP (or a direct DCS
  request, which on T8132 is PMP's job), and that needs the GPU firmware side
  (whatever MTR expects to be configured) before PMP can stay on.

## Root cause of the GPU crash (same day)

MTR is the GPU's temperature-sensor (metrology) block. Read from the running
G16 firmware (mBoot-18000.161.10; code at GPU VA 0xfffffc0000d28000, found by
walking iBoot's UAT handoff tables; dumps stay local, not published):

- `agfMTRAlarmHandler` (0xfffffc0000d5c814) loads a sensor mask from offset
  0x3b58 of the hardware-data block the driver builds. For each set bit i it
  reads MTR status at register 0x1008 + i * 0x200 (alarm bits 27:24). No set
  bit, or no status in any masked sensor, ends in "Received MTR Alarm interrupt
  from GPU but no match found in MTR hardware!" (the crash we saw).
- A matched alarm is then "handled" only through the fast-die masks at 0x2f08
  (shifted by the word at 0x2f14) or 0x2268; otherwise "MTR Alarm interrupts
  not handled!" (also fatal).
- At start-up the firmware arms alarms only for sensors in those masks: for
  each bit of 0x2268 it writes 0x1000000 to MTR 0x1004 + i * 0x200, for 0x3b58
  0x10000 (when a firmware flag is set), for 0x2f08 1 << (24 + shift).
- linux-gravity-m4's G16 driver (g16_platform.rs `hwdata()`) leaves 0x2268,
  0x2f08 and 0x3b58 at 0. siliconforest-linux's M3 (T8122) board writes the
  ADT fast-die mask to 0x2268 and 0x2f08 and 0x4b48 to 0x3b58 (plus 1 at
  0x3b60): the same offsets in the same object.
- PMP's ADT temp-sensor table includes "MTR_TOP_AGX" with a 109 C threshold
  (the CPU and ANE sensors at 110/125 C). PMP arms that GPU sensor itself; the
  GPU firmware, told to watch no sensors, has nothing to match the interrupt.

Across known chips the alarm mask contains the fast-die mask (M1 0x12/0x12, M2
0x6800/0x6800, M1 Pro/Max 0x80/0x90 per byte, M3 0x4248/0x4b48). The M4
driver's fast-die controller uses 0x6958 (bundle +0x75e8), the likely set.

Fix to test: write the sensor masks at 0x2268, 0x2f08 and 0x3b58 (kernel
parameters, default off), and bisect with the two fatal messages: "no match"
means the alarming sensor is outside the 0x3b58 mask, "not handled" means it is
inside it but outside the fast-die masks.

## Mask fix test (release 10)

asahi_m4 gained three parameters (default 0, data unchanged): mtr_alarm
(power-parameter object +0x3b58, bundle 0x8ed8), mtr_fast_die (+0x2268 and
+0x2f08) and mtr_alarm_flag (+0x3b60). (Release 9 wrote them into the
hardware data at bundle +0 by mistake and changed nothing.) With PMP on and
mtr_alarm=0x6958:

- The G16 firmware no longer crashes at boot (it did on releases 8 and 9).
- The first GPU job fails within 7 ms ("failed Event kind=4", stamp never
  written); no failed events on the normal kernel.
- CPU DRAM reads stay at 21 GB/s (69-73 without PMP).
- Two DCP (display) co-processor crashes at boot, new to this boot; the
  login screen still came up.

So the mask removes the fatal alarm, but PMP and the G16 firmware still don't
cooperate, and PMP keeps DRAM parked low. Next suspect: the GPU firmware's
channel to PMP (older chips map a "PMPDoorbell" region; the G16 driver maps
none) through which it would request GPU and DRAM performance.

## Why the GPU job stalls and DRAM stays low (release 10 analysis)

- The failed event is kind 4 with event_slot -1 and counter 0: in Asahi's
  older-firmware numbering that is the firmware's own GPU timeout with no
  slot. The G16 driver only handles kinds 1, 6, 7 and 13.
- PMP's ADT dcs-bw-threshold table has six DCS (DRAM) states with up/down
  thresholds (16.16 GB/s): up at 19.9, 39.9, 58.0, 74.3 and 87.0 GB/s. Our
  measurements fit: no PMP, 70-82 GB/s (iBoot leaves DCS in state 4, <= 87);
  macOS ~100 GB/s (state 5); PMP running, 21 GB/s (state 0-1).
- PMP raises DCS from bandwidth monitors and performance requests. Our PMP
  driver performs only the start-up handshake; nothing sends PMP performance
  requests (the same is true of GravityLinux and aurora-silicon's PMP work so
  far), so it holds DRAM, and probably the GPU, low.
- The G16 firmware knows a kAGFIPIORegionTypePMPDoorbell region, but among
  Asahi's tables only M1 (T8103) maps one; the region names are not
  referenced from G16 code, so the slot mapping is not visible there.

Next: release 11 = release 10 with apple_pmp.verbose=1 by default, to log
every descriptor PMP asks for and which tunables it does not receive.

## Handshake log and monitors (releases 11 and 12)

Release 11 (apple_pmp.verbose=1): PMP advertised 450 descriptors (405 wire
keys, four AdvertiseDone batches); only two tunables were missing from the
ADT copy (pmc-max-bwr-latency-us, lts-acsk-tddb-config). About 40 are
"<block>-monitor" switches (dcs, amcc, soc-ni0..5, soc-aon, soc-rest, eacc0,
pacc0, agx, ane0, isp, disp, dispext0/1, scodec, ave, avd, msr, jpeg, ltr,
atc0..3, ans, pcie, gfxc, sbr, sep, sio). The 115-pmp driver sets only dcs,
disp and dispext0/1 to 1. Release 11 also booted with no co-processor
crashes (release 10 had two DCP crashes).

Release 12 sets every monitor to 1 (34 initialised):

| | no PMP (r7) | PMP, 4 monitors (r10/r11) | PMP, all monitors (r12) |
|---|---:|---:|---:|
| CPU read, 1 thread | 34 GB/s | 18 GB/s | 9.6 GB/s |
| CPU read, 10 threads | 69-73 GB/s | 21 GB/s | 13.3 GB/s |
| GPU job | runs | firmware timeout (kind 4) | firmware timeout (kind 4) |

PMP acts on the monitors, but in the power-saving direction: nothing votes
for performance, so it lowers DRAM further. The missing piece is a
performance vote. aurora-silicon/linux m4/pr1-basic-bringup does this
through PMC (0x382800000: voters at +0x10000, rails at 0x3828aa000, agent
stride 0x4000, AP agent 3, dcs_max 5, pending bit at voters + 4,
apple,static-voters = <3>) with CLPC voting DCS 5 / SOC 3 under CPU or GPU
load; their G16 maps the PMP report pages (slots 9/10, which the GravityLinux
G16 driver also maps) and places a PMP AGX vote before RUN. Porting PMC/CLPC
voting is the next step; until then PMP stays off.
